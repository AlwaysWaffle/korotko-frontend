# Техническое задание: backend сервиса сокращения ссылок

## 1. Цель и контекст

Фронтенд — React/TypeScript-приложение для регистрации и входа, создания коротких ссылок, управления ими и просмотра статистики переходов. Пользователь работает со своими ссылками в личном кабинете.

Нужно реализовать API на FastAPI с PostgreSQL, которое обслуживает все вызовы из `src/api/client.ts`: регистрацию, вход, профиль, список и управление ссылками, а также статистику. Контракт ответов должен соответствовать интерфейсам `src/api/types.ts`. Клиент отправляет JSON и ожидает для списков непосредственно JSON-массив, а не объект-обёртку.

## 2. Инструменты и стек

- Python 3.12+
- FastAPI, Uvicorn
- Pydantic v2
- SQLAlchemy 2.x, Alembic
- PostgreSQL
- JWT для access token
- pytest
- Docker Compose

Redis, брокер сообщений и отдельный кэш фронтендом не требуются. Механизм учёта кликов и агрегации статистики выбирает реализация backend; при необходимости его можно добавить без изменения API-контрактов.

## 3. Запуск

Предлагаемые команды для backend-проекта:

```bash
# Docker Compose
docker compose up --build -d
docker compose exec api alembic upgrade head

# Логи и остановка
docker compose logs -f api
docker compose down

# Локально (PostgreSQL должен быть запущен и доступен)
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Адрес API, который ожидает фронтенд по умолчанию: `http://localhost:8000` (`VITE_API_URL` из `.env.example`). Swagger UI: `http://localhost:8000/docs`; OpenAPI: `http://localhost:8000/openapi.json`.

Для локального запуска Vite стандартный origin фронтенда — `http://localhost:5173`; добавить его в `CORS_ORIGINS`. Если порт или origin фронтенда изменён, обновить список. Переменные окружения backend:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | DSN PostgreSQL, например `postgresql+psycopg://app:change-me@localhost:5432/shortener` |
| `JWT_SECRET_KEY` | Секрет подписи JWT; задать отдельное надёжное значение вне репозитория |
| `JWT_ALGORITHM` | Алгоритм подписи, например `HS256` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Срок жизни access token; конкретное значение — решение реализации |
| `CORS_ORIGINS` | Разрешённые origins через запятую, минимум `http://localhost:5173` |
| `PUBLIC_BASE_URL` | Публичный origin коротких ссылок; локально `http://localhost:8000`, без завершающего `/` |
| `HOST` | Адрес bind для Uvicorn, локально `0.0.0.0` |
| `PORT` | Порт API, локально `8000` |

`PUBLIC_BASE_URL` нужен, чтобы формировать поле `short_url`; фронтенд использует его для отображения, копирования и открытия ссылки. Для рабочего окружения требуется публичный HTTPS-origin. Файл `.env` фронтенда в проекте не обнаружен; параметры клиента заданы в `.env.example`.

## 4. Модель данных

Ниже — минимальная схема, выведенная из полей, отправляемых клиентом и отображаемых им. Типы SQL указаны как рекомендуемые; реализация может выбрать эквиваленты с теми же ограничениями.

### `users`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | `BIGINT` или `INTEGER` | PK; во фронтенде число |
| `email` | `VARCHAR` | NOT NULL, уникальный индекс; нормализованный email для входа |
| `password_hash` | `VARCHAR` | NOT NULL; хранить только стойкий хеш, никогда не возвращать клиенту |
| `created_at` | `TIMESTAMPTZ` | NOT NULL; ISO 8601 в API |

### `links`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | `BIGINT` или `INTEGER` | PK; во фронтенде число |
| `user_id` | `BIGINT` или `INTEGER` | NOT NULL, FK → `users.id`, индекс; владелец |
| `code` | `VARCHAR` | NOT NULL, UNIQUE; публичный короткий код |
| `original_url` | `TEXT` | NOT NULL; исходный URL |
| `expires_at` | `TIMESTAMPTZ` | NULL; срок действия |
| `is_active` | `BOOLEAN` | NOT NULL, default `true` |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |

Индексы: уникальный индекс по `code`; индекс по `(user_id, created_at, id)` для выборки страниц; индекс по `(user_id, is_active)` для фильтра. Удаление пользователя должно не оставлять доступных ему ссылок (конкретную политику удаления выбрать при реализации).

### Данные переходов и аналитики

Чтобы отвечать на статистические запросы, backend должен сохранять как минимум ссылку, время перехода и источник перехода; для `unique_visitors` также нужен идентификатор посетителя или иной способ дедупликации. Возможная отдельная таблица `clicks`: `id`, `link_id` (FK/индекс), `clicked_at` (`TIMESTAMPTZ`, индекс), `referrer` (nullable `TEXT`), `visitor_key` (тип и срок хранения выбрать). Поля и политика дедупликации — допущение: фронтенд не задаёт способ измерения аналитики.

## 5. Ожидаемое API

Все пути ниже указаны относительно корня API `VITE_API_URL`; префикс `/api` клиентом не добавляется. Запросы с телом отправляются с `Content-Type: application/json`. Успешные коды, кроме обработки `401`, прямо клиентом не проверяются; указаны рекомендуемые обычные коды. Ошибки должны иметь FastAPI-формат `{"detail": ...}`. Для ошибок валидации допустим стандартный FastAPI `detail`-массив с `loc` и `msg`: клиент показывает эти сообщения пользователю.

### 5.1 `POST /auth/register`

- Токен: не нужен.
- Query: нет.
- Тело:

```json
{
  "email": "user@example.com",
  "password": "secret123"
}
```

  Оба поля обязательны. Фронтенд требует корректный email средствами HTML и пароль минимум 6 символов.
- Успех: `204 No Content` (клиент игнорирует ответ).
- Ошибки: `422` — некорректный email/пароль, отсутствующее поле; `409` — email уже зарегистрирован. Пример: `{"detail":"Email уже зарегистрирован."}`.
- Вызывается из `src/pages/RegisterPage.tsx` на `/register`; метод `api.register` в `src/api/client.ts`.

### 5.2 `POST /auth/login`

- Токен: не нужен.
- Query: нет.
- Тело:

```json
{
  "email": "user@example.com",
  "password": "secret123"
}
```

  Оба поля обязательны. JSON, не OAuth2 form data.
- Успех: `200`; поля `access_token` и `token_type` обязательны для клиента:

```json
{
  "access_token": "<jwt>",
  "token_type": "bearer"
}
```

- Ошибки: `401` — неверный email или пароль (`{"detail":"Неверный email или пароль."}`); `422` — невалидный запрос.
- Вызывается из `src/pages/LoginPage.tsx` на `/login`; метод `api.login` в `src/api/client.ts`.

### 5.3 `GET /auth/me`

- Токен: обязателен, `Authorization: Bearer <access_token>`.
- Query и тело: нет.
- Успех: `200`:

```json
{
  "id": 1,
  "email": "user@example.com",
  "created_at": "2026-10-29T12:00:00Z"
}
```

  `created_at` — ISO 8601; поля соответствуют `User`.
- Ошибки: `401` — отсутствующий, просроченный или неверный токен.
- Вызывается из `src/components/ProtectedLayout.tsx` для защищённых страниц; метод `api.me` в `src/api/client.ts`.

### 5.4 `GET /links`

- Токен: обязателен.
- Query:
  - `limit: integer` — клиент всегда передаёт `8`; в mock-реализации значение по умолчанию `10`. Backend должен поддержать `limit`; рекомендуемое ограничение `1..100`.
  - `offset: integer` — клиент всегда передаёт значение от `0` с шагом `8`; в mock-реализации значение по умолчанию `0`. Ограничение `>= 0`.
  - `is_active: boolean` — необязательный фильтр; отсутствует при выборе «Все», `true` для активных, `false` для выключенных.
- Тело: нет.
- Успех: `200`, непосредственный массив `LinkItem` (включая пустой массив, не `null`):

```json
[
  {
    "id": 1,
    "code": "launch",
    "short_url": "http://localhost:8000/launch",
    "original_url": "https://example.com/products/new-launch",
    "expires_at": null,
    "is_active": true,
    "created_at": "2026-10-27T12:00:00Z"
  }
]
```

  Каждый объект содержит `id`, `code`, `short_url`, `original_url`, `expires_at` (строка ISO 8601 или `null`), `is_active`, `created_at`. `clicks` в типе `LinkItem` необязателен: UI списка отдельно запрашивает статистику и подставляет `total_clicks`; возвращать `clicks` можно, но клиент на это не полагается.
- Ошибки: `401` — токен; `422` — query не прошёл валидацию.
- Вызывается из `src/pages/LinksPage.tsx` на `/links`; метод `api.links` в `src/api/client.ts`.

### 5.5 `POST /links`

- Токен: обязателен.
- Query: нет.
- Тело:

```json
{
  "original_url": "https://example.com/page",
  "custom_code": "my-link",
  "expires_at": "2026-12-01T10:30:00.000Z"
}
```

  `original_url` обязателен. `custom_code` и `expires_at` необязательны и отсутствуют в JSON, если не заданы. Код из формы соответствует `[A-Za-z0-9_-]+`. `expires_at` клиент конвертирует из локального `datetime-local` в ISO UTC; сервер должен принимать дату-время с часовым поясом. Без срока поле ответа должно быть `null`.
- Успех: `201`; созданный `LinkItem`, например:

```json
{
  "id": 42,
  "code": "my-link",
  "short_url": "http://localhost:8000/my-link",
  "original_url": "https://example.com/page",
  "expires_at": "2026-12-01T10:30:00Z",
  "is_active": true,
  "created_at": "2026-10-29T12:00:00Z",
  "clicks": 0
}
```

- Ошибки: `401` — токен; `422` — невалидный URL, код или дата; `409` — занятый `custom_code`/коллизия генерируемого кода. Пример: `{"detail":"Короткий код уже занят."}`.
- Вызывается из формы `src/pages/LinksPage.tsx` на `/links`; метод `api.createLink` в `src/api/client.ts`.

### 5.6 `GET /links/{id}`

- Токен: обязателен.
- Path: `id: integer`, положительный.
- Query и тело: нет.
- Успех: `200`, один полный `LinkItem` (пример — в 5.5).
- Ошибки: `401` — токен; `404` — ссылка не существует или принадлежит другому пользователю. Рекомендуется не раскрывать наличие чужих ресурсов.
- Вызывается из `src/pages/StatsPage.tsx` на `/links/:id/stats`; метод `api.link` в `src/api/client.ts`.

### 5.7 `PATCH /links/{id}`

- Токен: обязателен.
- Path: `id: integer`, положительный.
- Query: нет.
- Тело — частичное обновление, все поля необязательны; клиент фактически отправляет переключение статуса:

```json
{
  "is_active": false
}
```

  Также контракт `UpdateLinkInput` допускает `original_url` и `expires_at`; `expires_at` может быть `null` для сброса срока.
- Успех: `200`, обновлённый полный `LinkItem`.
- Ошибки: `401` — токен; `404` — нет ссылки у пользователя; `422` — некорректное поле/дата/URL.
- Вызывается из `src/pages/LinksPage.tsx` на `/links`; метод `api.updateLink` в `src/api/client.ts`.

### 5.8 `DELETE /links/{id}`

- Токен: обязателен.
- Path: `id: integer`, положительный.
- Query и тело: нет.
- Успех: `204 No Content` (клиент не читает тело).
- Ошибки: `401` — токен; `404` — ссылка не существует или принадлежит другому пользователю.
- Вызывается из `src/pages/LinksPage.tsx` на `/links`; метод `api.deleteLink` в `src/api/client.ts`.

### 5.9 `GET /links/{id}/stats`

- Токен: обязателен.
- Path: `id: integer`, положительный.
- Query и тело: нет.
- Успех: `200`:

```json
{
  "total_clicks": 128,
  "unique_visitors": 87
}
```

  Оба поля — целые числа `>= 0`.
- Ошибки: `401` — токен; `404` — ссылка не существует или принадлежит другому пользователю.
- Вызывается из `src/pages/LinksPage.tsx` по одному разу на каждую ссылку текущей страницы и из `src/pages/StatsPage.tsx`; метод `api.stats` в `src/api/client.ts`.

### 5.10 `GET /links/{id}/stats/daily`

- Токен: обязателен.
- Path: `id: integer`, положительный.
- Query:
  - `from: string` — обязательная дата `YYYY-MM-DD`.
  - `to: string` — обязательная дата `YYYY-MM-DD`.
  - Интерфейс выбирает включительный период; начальное значение — последние 14 календарных дат, включая сегодня. Ограничения `from <= to`, `to` не позже сегодняшнего дня по локальной дате пользователя. Верхний лимит периода фронтендом не задан.
- Тело: нет.
- Успех: `200`, непосредственный массив, не `null`; элемент на день имеет `date` (`YYYY-MM-DD`) и `clicks` (целое `>= 0`). Вернуть даты включительно для всего диапазона, в том числе с нулём:

```json
[
  {"date":"2026-10-28","clicks":12},
  {"date":"2026-10-29","clicks":0}
]
```

- Ошибки: `401` — токен; `404` — ссылка отсутствует/чужая; `422` — невалидная дата, `from > to` или недопустимый диапазон.
- Вызывается из `src/pages/StatsPage.tsx` на `/links/:id/stats`; метод `api.daily` в `src/api/client.ts`.

### 5.11 `GET /links/{id}/stats/referrers`

- Токен: обязателен.
- Path: `id: integer`, положительный.
- Query и тело: нет.
- Успех: `200`, непосредственный массив, не `null`:

```json
[
  {"referrer":"google.com","clicks":54},
  {"referrer":"","clicks":12}
]
```

  `referrer` — строка; пустая строка допустима и показывается как прямой переход. `clicks` — целое `>= 0`. При отсутствии данных вернуть `[]`.
- Ошибки: `401` — токен; `404` — ссылка отсутствует/чужая.
- Вызывается из `src/pages/StatsPage.tsx` на `/links/:id/stats`; метод `api.referrers` в `src/api/client.ts`.

## 7. Общие требования

- **Аутентификация:** `POST /auth/login` возвращает JWT в `access_token`, `token_type` — `bearer`. Фронтенд хранит token в `localStorage` под ключом `shortener_access_token` и передаёт его как `Authorization: Bearer <token>` во всех вызовах с `auth: true`. Refresh token и endpoint выхода клиентом не используются.
- **401:** при любом HTTP `401` клиент удаляет токен и отправляет событие `shortener:unauthorized`; `ProtectedLayout` перенаправляет пользователя на `/login`. Для ошибок другого статуса клиент читает `detail`; при ошибках FastAPI-валидации отображает `msg` и последнее значение `loc`.
- **Профиль:** `GET /auth/me` запускается при защищённом layout. Ошибка этого запроса проглатывается компонентом; если это `401`, срабатывает общий обработчик, другие ошибки не показываются.
- **Идентификаторы и даты:** `id` числовой. `created_at` и `expires_at` — ISO 8601 с timezone; nullable только `expires_at`. Даты статистики — строки `YYYY-MM-DD`; клиент отправляет `from`/`to` именно в таком формате.
- **Списки и пагинация:** `GET /links` должен вернуть плоский JSON-массив. Клиент загружает страницы по 8 записей с `limit`/`offset`; пагинация offset-based. Никакого `total` frontend не читает. Для daily/referrers также нужны непосредственные массивы.
- **Валидация:** соответствовать HTML-ограничениям формы (email, пароль минимум 6 символов, URL, код из латинских букв/цифр/`_`/`-`, дата срока). Серверная валидация обязательна независимо от браузера. Ошибки — неуспешный HTTP-статус и `{"detail": ...}`, не успешный ответ с ошибкой внутри.
- **Владение ресурсами:** все операции над ссылками и аналитикой ограничиваются текущим владельцем из токена; не доверять переданному `user_id` (клиент его не отправляет). Для чужого/несуществующего ID использовать одинаковый `404`.
- **Безопасность:** пароли хранить только в виде стойкого хеша; сравнение — через проверенную password-hashing библиотеку. Валидировать схемы данных, не возвращать `password_hash`, ограничить CORS заданными origins, подписывать JWT секретом из окружения.
- **CORS:** разрешить origin фронтенда (обычно `http://localhost:5173`), методы и заголовки, необходимые JSON-запросам и `Authorization`. Не использовать wildcard origins для production.
- **Структура:** разделить `routers`, `services`, `models`, `schemas`; настройки/подключение БД и зависимости аутентификации вынести отдельно. Миграции — Alembic.
- **Совместимость ответа:** не менять имена полей и типы из `src/api/types.ts`; клиент не использует обёртки вида `{items: [...]}`.

## 8. Этапы и критерии приёмки

1. **Основа проекта и БД.** Поднять FastAPI, PostgreSQL и Compose; добавить конфигурацию, SQLAlchemy и миграции. Готово, если Compose запускается, health/API доступны, миграция создаёт схему, Swagger открывается.
2. **Регистрация и вход.** Реализовать `POST /auth/register`, `POST /auth/login` и выпуск access JWT. Готово, если фронтенд регистрирует пользователя, повторная регистрация возвращает `409` с `detail`, логин выдаёт оба поля токена, неверные данные — `401`.
3. **Профиль и защита.** Реализовать `GET /auth/me` и bearer-проверку. Готово, если запрос с токеном возвращает `User`, а без токена/с истёкшим токеном — `401`; фронтенд перенаправляет на вход.
4. **CRUD ссылок.** Реализовать список с фильтрами и offset pagination, создание, получение, частичное обновление и удаление. Готово, если `/links` отображает страницы по 8, фильтры активных работают, custom code и срок сохраняются, переключение статуса и удаление обновляют список, а чужая ссылка не доступна.
5. **Переходы и агрегаты.** Обеспечить подсчёт переходов, уникальных посетителей, daily series и referrers. Готово, если статистическая страница загружает ссылку и три агрегата, получает массивы требуемой формы, а диапазон дат включает границы и дни без переходов.
6. **Сквозная проверка и эксплуатация.** Добавить pytest для успешных и ошибочных сценариев, CORS-настройки и инструкцию запуска. Готово, если сборка фронтенда с `VITE_USE_MOCK=false` проходит основные сценарии login/register, список, создание/управление ссылкой и аналитика без несовпадения контрактов.

## 9. Вне рамок

- Изменения React-кода, UI, маршрутизации и mock-режима.
- Новые пользовательские функции и API, которых клиент не вызывает (поиск, сортировка, bulk-операции, экспорт, refresh token, сброс пароля, OAuth, административная панель).
- Реализация клиентского endpoint редиректа как одного из перечисленных API-вызовов: фронтенд не вызывает его через `src/api/client.ts`. При этом README фронтенда указывает, что публичный `/{code}` редирект выполняет backend; если сервис должен реально сокращать и перенаправлять публичные ссылки, это отдельная необходимая runtime-функция, не входящая в перечень 11 API-операций.
- Redis и кэш: фронтенд не требует конкретного кэширования.

## 10. Расхождения и допущения

### Допущения

- Для регистрации выбран ответ `204`, для создания ссылки — `201`; клиенту достаточно любого успешного ответа, но успешные ответы и поля заданы контрактами.
- Дубликат email и `custom_code` возвращается как `409`; во фронтенде дубликат кода в mock превращается в обычную ошибку, HTTP-код не задан.
- Автоматический `code` должен генерироваться backend и быть уникальным; длина/алфавит автоматического кода фронтендом не специфицированы.
- `expires_at` — абсолютная дата-время, передаваемая клиентом в UTC; поведение просроченной ссылки при переходе и приостановки ссылки определяется backend, UI лишь отображает истечение срока.
- `unique_visitors` предполагает серверный механизм идентификации и дедупликации посетителей. Фронтенд не задаёт идентификатор посетителя, период дедупликации или требования приватности.
- Аналитика и хранение реферера основаны на фактических переходах; правила нормализации, приватности, хранения IP/cookie и обработки отсутствующего `Referer` должны быть выбраны реализацией.
- `PUBLIC_BASE_URL` используется для полного `short_url`; ожидаемый формат — абсолютный URL с origin и `/{code}`.
- Для диапазона daily фронтенд начально передаёт 14 дней включительно и не устанавливает максимальную длительность. Защитный лимит диапазона стоит определить в реализации и документировать, чтобы не ломать допустимый сценарий.
- Для `limit` рекомендован верхний предел 100; фронтенд использует 8. Детали политики удаления пользователя фронтенд не определяет.

### Неясности и возможные проблемы клиента

- В `LinkItem` поле `clicks` необязательно, но экран списка получает число кликов отдельным `GET /links/{id}/stats` для каждой записи. Это создаёт N+1 HTTP-запросов; backend не должен менять ответ `/links` на обёртку. При текущем контракте статистика должна быть доступна для каждой ссылки.
- Компонент списка блокирует переход на следующую страницу, если пришло меньше 8 записей; это корректно только если API возвращает настоящие страницы без искусственного усечения.
- В `StatsPage` все четыре запроса выполняются параллельно; ошибка любого из них показывает ошибку всей загрузки.
- Изменение срока через `PATCH` предусмотрено типом, но форма редактирования срока в UI отсутствует.
- README явно говорит, что редирект `/{code}` делает backend, но такой путь не вызывается API-клиентом. Если требуется полный работающий сервис сокращения, реализацию редиректа и её поведение при отключённой/истёкшей ссылке нужно подтвердить отдельно.
- `.env.example` задаёт только клиентские `VITE_API_URL` и `VITE_USE_MOCK`; настоящего `.env` нет. Origin фронтенда `http://localhost:5173` взят из стандартного порта Vite и должен быть скорректирован, если запуск идёт на другом порту/хосте.
- В mock авторизация принимает тестовые данные и не отражает серверные статусы ошибок; контракт backend следует определять по реальному HTTP-клиенту и формам, а не по mock-режиму.

### Вопросы, которые решает разработчик backend

1. Какие параметры JWT (срок жизни, ротация/отзыв) и политика хранения/защиты токена будут использоваться? Фронтенд умеет только хранить один access token и реагировать на `401`.
2. Как определять уникального посетителя и каков период дедупликации без нарушения требований приватности?
3. Каковы правила и максимальная длина автоматического/пользовательского кода, срок хранения click events и максимальный диапазон статистики?
4. Какая политика редиректа для несуществующей, отключённой или истёкшей ссылки? Нужен ли публичный `/{code}` endpoint в первой версии?
5. Разрешить ли регистрацию без подтверждения email, и какие правила кроме минимума в 6 символов применить к паролю?
6. Должно ли удаление ссылки удалять историю кликов или сохранять агрегаты?

**Итог:** найдено 11 операций API. Основные допущения — коды успешных ответов регистрации/создания, конфликты `409`, алгоритм генерации кода, аналитика уникальных посетителей и ограничения диапазона дат. Решения разработчика требуются по вопросам выше, в особенности по редиректу `/{code}` и механизму уникальных посетителей.
